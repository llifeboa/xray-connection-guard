# Xray Connection Guard

Банит IP клиента на **10 минут**, если за **5 минут** обнаружены **5 BitTorrent-потоков к 5 разным IP пиров**. Бан блокирует весь входящий и исходящий трафик с этим IP **на всех портах** и затрагивает все аккаунты за этим IP.

Нужен сервер на **Debian 12+ или Ubuntu 22.04+ с systemd**. Xray должен работать в сети хоста; для Docker — `network_mode: host`.

## 1. Установить

```bash
git clone https://github.com/llifeboa/xray-connection-guard.git
cd xray-connection-guard
sudo bash manage.sh install
```

Установщик сам ставит зависимости, **Suricata 8.0.8 и nDPI 4.14**, создаёт конфиги guard и Suricata, правило BitTorrent, правила NFQUEUE и сервисы systemd. Первая сборка может занять несколько минут. Если подходящая Suricata с nDPI уже установлена, используется она. После настройки Xray останется выполнить `enable`.

## 2. Добавить журнал и метку в Xray

В Remnawave открой **Config Profile нужной ноды**, в Marzban — редактор конфигурации Xray. Примени изменения через панель.

**Журнал: выбери вариант своей панели и добавь `log` в корень JSON.**

Для **Remnawave**, чтобы пользоваться штатным `xlogs`:

```json
{
  "log": {
    "access": "",
    "logLevel": "info",
    "maskAddress": ""
  }
}
```

Пустой `access` направляет записи в [stdout Xray](https://xtls.github.io/en/config/log.html#logobject). Посмотреть их можно командой `sudo docker exec remnanode xlogs`.

Для журнала Xray под Supervisor guard при старте и затем каждые **10 минут** проверяет `stdout_logfile_maxbytes` в `/etc/supervisord.conf` найденного контейнера. Если лимит меньше **100 МБ**, guard увеличивает его до `100MB` и **перезапускает этот контейнер**, кратковременно прерывая подключения через ноду. При лимите `100MB` или больше, а также при `0` (без ограничения размера), файл не меняется и перезапуска нет. Отсутствующий параметр считается [штатным лимитом Supervisor `50MB`](https://supervisord.org/configuration.html#program-x-section-settings).

Проверка работает в фоне; её результат и ошибки записываются в журнал guard. При ошибке применения изменения guard повторит попытку через 10 минут. Контейнеры с другим способом ведения журнала пропускаются. Настройки при `--check` только проверяются: контейнер не изменяется и не перезапускается.

Для **Marzban**, с журналом в файле:

```json
{
  "log": {
    "access": "/var/lib/marzban/access.log",
    "logLevel": "info",
    "maskAddress": ""
  }
}
```

Каталог журнала должен быть доступен Xray на запись.

**Метка: в каждый используемый `freedom`-outbound добавь `streamSettings.sockopt.mark`:**

```json
{
  "tag": "DIRECT",
  "protocol": "freedom",
  "settings": {},
  "streamSettings": {
    "sockopt": {
      "mark": 1481785689
    }
  }
}
```

Сохрани свой `tag` и остальные параметры: это пример одного outbound, не замена всего массива. Метка **`1481785689`** (`0x58524159`, «XRAY») уже прописана в автоматической настройке NFQUEUE. [Для установки метки Xray нужны права `CAP_NET_ADMIN`](https://xtls.github.io/en/config/transports/sockopt.html#sockoptobject).

У пользователей должен быть непустой `email`, а в access-строках — IP:порт клиента и назначения. Панели обычно добавляют `email` сами.

## 3. Включить

Из каталога проекта:

```bash
sudo bash manage.sh enable
sudo journalctl -fu xray-connection-guard
```

Команда сама находит Xray, его журнал и часовой пояс, заполняет конфиг guard, запускает Suricata с NFQUEUE и включает guard с автозапуском. Для Remnawave читается тот же журнал, что и `xlogs`; имя контейнера и путь определяются автоматически. Для Marzban проверяются открытые Xray файлы и стандартные пути access-журнала. Автонастройка повторяется перед каждым запуском сервиса.

**Вручную конфиг guard заполнять не нужно.** Порог 5 потоков / 5 IP пиров и бан на 600 секунд уже заданы. IP ноды определяются автоматически и проверяются каждые 10 минут; действующие баны сохраняются. Бан действует на всех портах.

Если на сервере несколько Xray-контейнеров, выбери нужный командой `sudo bash manage.sh enable --container ИМЯ`.

В `journalctl` при старте выводятся все рабочие параметры guard, включая найденные IP, источники журналов, пороги и область блокировки. Каждая проверка адресов логируется; при изменении указываются старые и новые IP. При ошибке проверки сохраняются последние адреса, а ошибка записывается в журнал.

После запуска проверяй новые подключения: старые строки журналов не учитываются. Посмотреть баны:

```bash
sudo bash manage.sh bans
```

В аудите `/var/log/xray-connection-guard/audit.jsonl` успешный бан отмечается как `banned-600s`. Частные, служебные, адреса самого сервера и `allowlist_cidrs` не банятся.

## Обновить установленный guard

Из каталога проекта на сервере:

```bash
git pull --ff-only
sudo bash manage.sh install
sudo bash manage.sh enable
```

После перезапуска начни новые подключения для проверки: guard читает журналы с момента своего запуска.

## Остановить guard и снять его IP-баны

```bash
sudo bash manage.sh off
```

Suricata продолжит проверять трафик. Команда останавливает guard и удаляет его временные IP-баны.

## Если банов нет

`Started mode=enforce` подтверждает режим блокировки. Строка `stats` показывает этапы обработки: `access` — распознанные записи Xray, `eve_lines` — прочитанные записи Suricata, `alerts` — подходящие заблокированные события BitTorrent, `matched` — сопоставления с клиентами, `bans` — успешные баны. `eve_ignored_*` указывает причину отбрасывания события.

Guard сопоставляет access-запись со временем начала потока `flow.start` из EVE: nDPI может определить BitTorrent спустя больше минуты. Если `flow.start` отсутствует или некорректен, используется время события. Окно «5 потоков к 5 пирам за 5 минут» отсчитывается по времени обнаружения.

Для XUDP guard также читает строки `proxy/freedom: connection opened to udp:… local endpoint …` из INFO-журнала Xray. Они связывают исходящий UDP-сокет с первоначальной access-записью клиента: следующие пиры могут использовать тот же сокет без новых access-записей. Привязка сохраняется, пока сокет открыт, даже после удаления старых строк журнала из истории guard. Состояние и inode сокета проверяются через `/proc/self/net/udp` и `udp6`; закрытый сокет, переиспользованный порт или перенос XUDP на другое входящее соединение не сохраняют прежнего владельца. Сопоставление первоначальных записей по адресу и времени остаётся вероятностным; несколько подходящих IP клиентов не дают бана.

`matched_by_udp_socket` показывает число BitTorrent-потоков, сопоставленных через UDP-сокет, а `udp_socket_bindings` — число проверенных сокетов. В строке `BitTorrent match` способ указан как `via=udp_socket` или `via=peer`.

При успешном сопоставлении строка `BitTorrent match` показывает IP клиента и прогресс `peers=…/5 flows=…/5`. `correlation_waits` считает потоки, которым пришлось ждать сопоставления, один раз на поток. Если время ожидания истекло, `BitTorrent flow unmatched` объясняет причину:

- `no_access_for_peer` — для этого IP:порта пира нет access-записи с тем же TCP/UDP-протоколом.
- `time_window` — запись есть, но её время не подходит; `nearest_access_delta_seconds` показывает разницу с началом потока.
- `client_ip_missing` — из подходящей записи не удалось получить IP клиента.
- `multiple_client_ips` — подходят несколько разных IP клиентов.
- `udp_socket_owner_missing` — исходящий UDP-сокет найден, но для его первоначального пира нет подходящей access-записи клиента.
- `udp_socket_unverified` — сокет закрыт, порт переиспользован, поток старше текущего сокета, произошёл перенос XUDP или состояние сокета нельзя подтвердить.

Если растёт только `access`, во время новой загрузки торрента проверь:

```bash
sudo nft list table inet xray_guard_inspect
sudo cat /proc/net/netfilter/nfnetlink_queue
sudo journalctl -u xray-ndpi -n 50 --no-pager
sudo tail -n 3 /var/log/xray-ndpi/eve.json
```

При растущем трафике через Xray нулевые счётчики `queue` в nftables указывают на проблему до Suricata: проверь метку `1481785689` в используемых outbound и применение профиля Xray. Счётчики очереди могут расти и при обычном трафике; для бана нужны распознанные BitTorrent-события к пяти разным IP пиров.

## Структура проекта

- `src/` — код guard, автонастройки и установки Suricata.
- `config/` — пример конфигурации guard.
- `systemd/` — файл сервиса guard.
- `tests/unit/` и `tests/integration/` — тесты; [команды запуска](tests/README.md).

`manage.sh` — установка и управление сервисом; запускается из корня проекта.
