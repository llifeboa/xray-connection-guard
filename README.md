# Xray Connection Guard

Инструкция для схемы **клиент → RU → выходная нода**, где RU пересылает трафик через VLESS-outbound: XHTTP/REALITY или RAW/REALITY с Vision либо без `flow`. Инспекция на RU работает с **IPv4**, через native TUN Xray.

Если RU сама выходит в интернет через `freedom`/`DIRECT`, используй [отдельный раздел для DIRECT](#direct).

## Что делает защита

| Компонент | Действие |
|---|---|
| Suricata + nDPI | Распознаёт BitTorrent и блокирует распознанные потоки. |
| Guard | Сопоставляет события Suricata с журналом Xray и находит исходный IP клиента. |
| Временный IP-бан | Если за 5 минут обнаружены 5 потоков к 5 разным IP пиров, блокирует IP клиента на 10 минут. |

**IP-бан действует на всех портах и протоколах**, включая другие подключения и аккаунты за тем же IP. Если SSH и тестовый клиент выходят с одного внешнего IP, бан затронет и SSH. Адрес администратора при необходимости добавляется в [список исключений](#allowlist).

Блокировка потока Suricata и IP-бан — разные действия: поток может быть уже заблокирован, хотя порог для бана IP ещё не достигнут. Начальные пакеты неизвестного протокола могут пройти до его распознавания.

## Где выполнять действия

| Место | Что здесь делать |
|---|---|
| Linux-хост **RU**, по SSH | Устанавливать guard, выполнять `manage.sh`, смотреть systemd и сетевые настройки. |
| Docker Compose **ноды RU** | Разрешить контейнеру Xray работу с TUN, если Xray запущен в Docker. |
| Панель → профиль Xray **ноды RU** | Настроить журнал, добавить TUN-inbound и outbound, изменить маршрутизацию. |
| Выходная нода | Сохранить её действующую конфигурацию: guard в этой схеме работает на RU. |

Все команды `bash` в основной инструкции выполняются **на хосте RU**, из каталога этого проекта. Команды `docker exec` также запускаются на хосте. JSON-блоки добавляются **в профиль Xray в панели**.

<a id="prepare"></a>
## 1. Подготовить RU

До настройки должен работать обычный маршрут **клиент → RU → выходная нода → интернет**. Сохрани копию рабочего профиля Xray на RU: она понадобится для возврата.

Требования:

- Debian 12+ или Ubuntu 22.04+ с systemd и доступом root/sudo.
- Xray на RU работает в сети хоста; для Docker требуется `network_mode: host`.
- Процесс Xray имеет доступ к `/dev/net/tun` и право `CAP_NET_ADMIN`.
- Подсеть `198.18.0.0/30` свободна. Это внутренняя подсеть TUN; публичный адрес RU менять не нужно.

**Проверенное ядро на RU — [Xray 26.11.9](https://github.com/XTLS/Xray-core/releases/tag/v26.11.9). Xray 26.3.27 для этой TUN-схемы на RU не подходит.** В [конфигурации TUN этой версии](https://github.com/XTLS/Xray-core/blob/v26.3.27/infra/conf/tun.go) ещё нет `gateway`: интерфейс создаётся, но IPv4 из примера ему не назначается. Это воспроизведено в Docker с Marzban. Также в стенде воспроизводится потеря UDP-назначения при смене пиров через один сокет. Клиенты 26.3.27 могут использовать RU 26.11.9.

**Сначала проверь ядро внутри контейнера RU**, а не версию панели или Xray на хосте. Например, для Marzban:

```bash
sudo docker exec marzban /usr/local/bin/xray version
```

Подставь имя своего контейнера. `manage.sh install` **не обновляет Xray** в Marzban/Remnawave, но проверяет версию именно работающего ядра через `/proc/PID/exe`, включая внешний бинарник в контейнере. По умолчанию установка рассчитана на TUN: требуется **Xray не ниже 26.11.9**, выбранного как проверенная нижняя граница. Старое ядро или неизвестный формат версии останавливают установку до копирования файлов guard и подготовки Suricata. Версия проверяется повторно при включении TUN-инспекции. На 26.3.27 сначала обнови ядро ноды и проверь обычное подключение, только затем меняй маршрут на TUN. Одного успешного `xray run -test` недостаточно: старое ядро может молча игнорировать неизвестный `gateway`.

Если в `.env` Marzban задан `XRAY_EXECUTABLE_PATH`, вместо `/usr/local/bin/xray` проверь именно этот путь: встроенный бинарник образа может оставаться старым, хотя панель использует другой. Версию работающего ядра также показывает API Marzban `/api/core`. Выбор внешнего бинарника описан в [инструкции Marzban по смене ядра](https://gozargah.github.io/marzban/en/examples/change-xray-version); изменять его нужно на RU, где создаётся TUN.

В проверенном образе Marzban 0.8.4 старый генератор REALITY-ключей не разбирает новый вывод `xray x25519`. Если после обновления ядра панель падает в `get_x25519`, сохрани существующий `privateKey` и укажи соответствующий ему `publicKey` в `streamSettings.realitySettings` публичного inbound. В стенде использовался этот вариант; менять ключи клиентов ради TUN не требуется.

### Если Xray запущен в Docker

Посмотри имя контейнера ноды:

```bash
sudo docker ps --format 'table {{.Names}}\t{{.Image}}'
```

В примерах имя контейнера — `remnanode`. Если у тебя другое, подставляй его в команды `docker exec` и параметр `--container`.

Открой `docker-compose.yml` или `compose.yaml`, которым запущена **нода RU**. Для Compose-установки путь часто можно получить так:

```bash
sudo docker inspect remnanode --format '{{ index .Config.Labels "com.docker.compose.project.config_files" }}'
```

В существующий сервис ноды добавь недостающие настройки:

```yaml
services:
  remnanode:
    network_mode: host
    cap_add:
      - NET_ADMIN
    devices:
      - /dev/net/tun:/dev/net/tun
```

Это **дополнение к существующему Compose**, а не полный файл. Сохрани имя своего сервиса, `image`, `environment`, `volumes` и остальные параметры. Если `cap_add` или `devices` уже есть, дополни их списки.

При `network_mode: host` убери `ports`, если они были: Xray слушает порты непосредственно на хосте, отдельная публикация портов не используется.

В каталоге этого Compose-файла примени изменения:

```bash
sudo docker compose up -d
```

Пересоздание контейнера разорвёт его текущие подключения. После запуска проверь, что обычный маршрут через ноду снова работает. Подробнее о [сети host в Docker Compose](https://docs.docker.com/compose/how-tos/networking/#change-the-network-mode).

Для Xray без Docker доступ к TUN и права на создание интерфейса должны быть выданы его системному сервису.

<a id="install"></a>
## 2. Установить guard на хост RU

Для первой установки:

```bash
git clone https://github.com/llifeboa/xray-connection-guard.git
cd xray-connection-guard
sudo bash manage.sh install
```

Если проект уже скачан, перейди в **его существующий каталог** и выполни:

```bash
git pull --ff-only
sudo bash manage.sh install
```

Установщик копирует исполняемые файлы в `/opt/xray-connection-guard/`, устанавливает зависимости, подготавливает конфиги и службы. При необходимости собирает **Suricata 8.0.8 + nDPI 4.14**; первая сборка занимает несколько минут. Подходящий установленный движок используется повторно.

Если работают несколько Xray-контейнеров, выбери RU уже при установке: `sudo bash manage.sh install --container remnanode`. Для проверки версии access-журнал ещё не нужен. Если Xray пока не запущен, установщик явно откладывает проверку до включения инспекции; это не означает, что совместимость ядра уже подтверждена. Для варианта DIRECT без TUN используй `sudo bash manage.sh install --inspection-mark`: версия определяется, но ограничение TUN к ней не применяется.

**После `install` ещё нужно настроить профиль Xray и выполнить `enable`.** Сам установщик профиль в панели не изменяет. Конфиг guard вручную заполнять не требуется.

<a id="logging"></a>
## 3. Включить журналы Xray в панели

Открой **профиль RU**: в Remnawave — Config Profile, назначенный нужной ноде; в Marzban — конфигурацию Xray. Если один профиль используется и на RU, и на выходной ноде, сначала сделай отдельный профиль для RU.

Поле `log` находится **в корне JSON**, на одном уровне с `inbounds`, `outbounds` и `routing`. Если оно уже существует, измени его, а не добавляй второй ключ `log`.

Выбери **один** вариант.

### Remnawave: журнал через xlogs

```json
{
  "log": {
    "access": "",
    "error": "",
    "logLevel": "info",
    "maskAddress": ""
  }
}
```

Пустые `access` и `error` направляют оба журнала в stdout Xray. Guard читает тот же журнал, который показывает `xlogs`. Параметры описаны в [документации журналов Xray](https://xtls.github.io/ru/config/log.html).

### Marzban или файловый журнал

```json
{
  "log": {
    "access": "/var/lib/marzban/access.log",
    "error": "/var/lib/marzban/access.log",
    "logLevel": "info",
    "maskAddress": ""
  }
}
```

Здесь **оба журнала пишутся в один файл**. Guard должен видеть и access-записи, и INFO-сообщения `proxy/freedom`: они нужны для привязки UDP/XUDP к исходному клиенту. Один access-файл без INFO для этого недостаточен.

Каталог должен существовать и быть доступен процессу Xray на запись. Если используется другой путь, укажи его одинаково в `access` и `error`; guard определяет источник автоматически.

У пользователей должен быть непустой `email`, а адреса в журнале должны оставаться немаскированными. Панели обычно заполняют `email` сами.

<a id="xray"></a>
## 4. Добавить TUN в профиль Xray на RU

Нужно **добавить один inbound, один outbound и заменить одно правило двумя**. Остальные части действующего профиля сохраняются.

Не применяй эти изменения на RU с Xray 26.3.27: клиентский трафик уйдёт в TUN без IPv4, и защита не запустится. Сначала выполни проверку версии из шага 1.

### 4.1. Определить свои имена

Найди в текущем JSON два существующих тега:

| Имя в примерах | Что это | Что указать у себя |
|---|---|---|
| `PUBLIC_RU_IN_2` | `tag` публичного inbound, к которому подключаются клиенты | Свой существующий тег inbound. |
| `TO_FREEDOM` | `tag` outbound, который отправляет трафик на выходную ноду | Свой существующий тег outbound. |
| `GUARD_TUN_IN` | Новый TUN-inbound | Оставь это имя в новых блоках. |
| `INSPECT_VIA_TUN` | Новый промежуточный outbound | Оставь это имя в новых блоках. |
| `xray-guard` | Имя Linux-интерфейса TUN | Оставь это имя в профиле и команде запуска. |

Если у твоего публичного inbound тег `VLESS_IN`, в правилах ниже вместо `PUBLIC_RU_IN_2` пиши `VLESS_IN`. Аналогично подставь реальный тег выхода вместо `TO_FREEDOM`.

### 4.2. Добавить объект в массив inbounds

**Куда:** в существующий массив `inbounds`, рядом с уже имеющимися inbound-объектами.

**Что добавить:**

```json
{
  "tag": "GUARD_TUN_IN",
  "protocol": "tun",
  "settings": {
    "name": "xray-guard",
    "mtu": 1500,
    "gateway": ["198.18.0.1/30"]
  }
}
```

Существующий публичный inbound с его портом и пользователями сохраняется. Новый объект создаёт TUN; назначать ему публичный порт не требуется.

Адрес TUN назначает сам Xray через `gateway`. Если подсеть занята, выбери свободную и измени `gateway`: guard использует фактический IPv4-адрес интерфейса.

### 4.3. Добавить объект в массив outbounds

**Куда:** в конец существующего массива `outbounds`.

**Что добавить:**

```json
{
  "tag": "INSPECT_VIA_TUN",
  "protocol": "freedom",
  "streamSettings": {
    "sockopt": {
      "interface": "xray-guard",
      "domainStrategy": "ForceIPv4"
    }
  }
}
```

Действующий outbound `TO_FREEDOM` сохраняется целиком, включая адрес выхода, UUID, ключи, XHTTP и REALITY. Привязка `interface: "xray-guard"` нужна только новому `INSPECT_VIA_TUN`.

`TO_FREEDOM` здесь — тег существующего выхода: его протоколом может быть VLESS/RAW/REALITY с `flow: "xtls-rprx-vision"`. Промежуточный `INSPECT_VIA_TUN` остаётся `freedom`, привязанным к TUN: он передаёт пакеты в точку инспекции до шифрования внешним VLESS-outbound.

`ForceIPv4` разрешает доменные назначения через DNS Xray в IPv4. Сохрани свои рабочие настройки DNS.

### 4.4. Заменить правило в routing.rules

**Куда:** в существующий массив `routing.rules`.

Найди прежнее правило, отправляющее публичный inbound сразу на выход:

```json
{
  "inboundTag": ["PUBLIC_RU_IN_2"],
  "outboundTag": "TO_FREEDOM"
}
```

**Замени его двумя правилами** в таком порядке:

```json
[
  {
    "inboundTag": ["GUARD_TUN_IN"],
    "outboundTag": "TO_FREEDOM"
  },
  {
    "inboundTag": ["PUBLIC_RU_IN_2"],
    "outboundTag": "INSPECT_VIA_TUN"
  }
]
```

Вставляются два объекта **внутрь уже существующего** `routing.rules`. Квадратные скобки массива у тебя уже есть; второй массив внутри него создавать не нужно. Между соседними объектами поставь запятые.

Эти правила должны стоять **до общих правил перенаправления**, которые иначе перехватят тот же трафик. Существующие запреты частных адресов и доменов сохрани. Если прежнее правило содержит несколько inbound-тегов, перенеси в TUN только выбранный inbound, а маршруты остальных сохрани.

Если Xray уже блокирует `protocol: ["bittorrent"] → BLOCK`, такие потоки не дойдут до Suricata. Для их учёта и IP-банов через guard убери это отдельное правило Xray.

Полный набор добавляемых объектов есть в [config/xray-tun.fragment.json](config/xray-tun.fragment.json). Это **фрагмент для профиля**, а не замена всей конфигурации и не файл настроек guard.

После изменения путь трафика выглядит так:

```text
клиент
  → PUBLIC_RU_IN_2
  → INSPECT_VIA_TUN
  → NFQUEUE / Suricata
  → xray-guard / GUARD_TUN_IN
  → TO_FREEDOM
  → выходная нода
  → сайт или пир
```

Для этой схемы оставь `autoSystemRoutingTable` незаданным. Выборочную маршрутизацию TUN настраивает guard; отдельные команды `ip address`, `ip route`, `ip rule` и `sysctl` выполнять не нужно.

**Не добавляй `autoSystemRoutingTable: ["0.0.0.0/0"]`.** Это системный default route, а не маршрут только клиентов: при его приоритете над физическим маршрутом можно потерять доступ к SSH и панели. Guard не отменяет маршруты, добавленные самим Xray.

<a id="start"></a>
## 5. Применить профиль и запустить защиту

1. Проверь итоговый JSON в панели и примени его **к ноде RU**. При проверке через CLI передавай полный итоговый конфиг: `xray run -test -c /путь/к/config.json`.
2. Дождись запуска Xray. Он должен создать `xray-guard` и назначить ему IPv4-адрес.
3. В SSH на хосте RU, из каталога проекта, выполни:

```bash
sudo bash manage.sh enable --inspection-interface xray-guard
```

Если на сервере несколько Xray-контейнеров, выбери нужный явно:

```bash
sudo bash manage.sh enable --inspection-interface xray-guard --container remnanode
```

Имя `remnanode` здесь — пример: используй имя своего контейнера из `docker ps`.

После переключения профиля на TUN трафик может не проходить до запуска инспекции. Поэтому сразу переходи к `enable`; перезапуск Xray также разрывает текущие соединения.

Команда автоматически:

- Находит журнал Xray и часовой пояс.
- Создаёт правила NFQUEUE, настраивает IPv4-маршрут и правило в отдельной таблице `14817`.
- Устанавливает `rp_filter=2` только для TUN-интерфейса.
- Запускает Suricata и guard, включает их автозапуск.

Если таблица или приоритет `14817` заняты другими настройками, запуск завершится ошибкой готовности; причина будет в журнале службы очереди. Совпадающие настройки прежней ручной установки используются без дублирования.

**Guard может перезапустить контейнер ноды**, если обнаружит слишком маленький лимит журнала Supervisor. Это кратковременно прервёт подключения; подробности — в [разделе о журналах](#log-maintenance).

<a id="verify"></a>
## 6. Проверить работу

### Службы

На RU:

```bash
sudo systemctl is-active xray-connection-guard.service xray-ndpi.service xray-connection-guard-queue.service
```

Ожидаются три строки `active`.

Открой журнал guard:

```bash
sudo journalctl -fu xray-connection-guard.service
```

В нём должна появиться строка `Started mode=enforce`. В выводимых guard настройках должно быть `"inspection": {"interface": "xray-guard"}`, а не режим метки. Для выхода из просмотра журнала нажми `Ctrl+C`: службы продолжат работать.

Служба guard сообщает systemd о готовности только после открытия access- и EVE-журналов. Поэтому успешный `enable`/`monitor` означает, что читатели журналов уже инициализированы, а не только создан процесс Python.

### TUN и маршрутизация

Эти команды только показывают настройки:

```bash
ip -4 address show dev xray-guard
ip -4 route show table 14817
ip -4 rule show
ip -4 route show default
```

Ожидаемый результат:

- На `xray-guard` есть `198.18.0.1/30` или адрес, указанный в твоём `gateway`.
- В таблице `14817` есть default route через `xray-guard`.
- Есть правило `priority 14817 oif xray-guard lookup 14817`.
- Основной default route остаётся через физическую сеть.

### Трафик и баны

Сначала проверь обычный сайт через клиентское подключение. Затем начни **новые** BitTorrent-соединения через RU: guard читает журналы с момента своего запуска, старые записи не учитываются.

При сопоставлении событий журнал показывает `BitTorrent match`, исходный `client_ip` и прогресс `peers=…/5 flows=…/5`. После достижения порога ожидаются `BAN APPLIED` и `banned-600s`.

Посмотреть баны:

```bash
sudo bash manage.sh bans
```

Один заблокированный поток или несколько потоков к одному IP пира не обязаны давать IP-бан. Для него нужны пять потоков **к пяти разным IP** в пределах пяти минут.

<a id="operate"></a>
## Повседневная эксплуатация

Все команды `manage.sh` запускаются на RU из каталога проекта.

| Задача | Команда |
|---|---|
| Включить IP-баны | `sudo bash manage.sh enable` |
| Перезапустить guard в текущем режиме | `sudo systemctl restart xray-connection-guard.service` |
| Посмотреть состояние guard и его банов | `sudo bash manage.sh status` |
| Посмотреть текущие баны и последние записи аудита | `sudo bash manage.sh bans` |
| Смотреть журнал guard | `sudo journalctl -fu xray-connection-guard.service` |
| Смотреть журнал Suricata | `sudo journalctl -u xray-ndpi.service -n 50 --no-pager` |
| Смотреть автонастройку TUN | `sudo journalctl -u xray-connection-guard-queue.service -n 50 --no-pager` |

Выбор интерфейса сохраняется в конфиге. После первой настройки повторный `enable` продолжает использовать TUN; заново указывать `--inspection-interface` не требуется.

### Остановить IP-баны, оставив инспекцию

```bash
sudo bash manage.sh off
```

Это останавливает guard, отключает его автозапуск и удаляет его временные IP-баны. **Suricata продолжает анализировать трафик и блокировать BitTorrent**, маршрутизация TUN сохраняется. Чтобы пакеты проходили без анализа, используй `sudo bash manage.sh disable`, как описано в [отключении анализа](#stop). Возвращать исходный профиль Xray для этого не нужно.

Если systemd не смог остановить или отключить guard, `off` возвращает ошибку, не снимает баны и не сообщает об успешном отключении. Ошибки чтения и удаления правил nftables также не подавляются; повторный `off` после успешной остановки допустим.

Если нужно продолжать собирать события без новых IP-банов:

```bash
sudo bash manage.sh monitor
```

`monitor` не снимает уже действующие баны. Для чистого переключения сначала выполни `off`, затем `monitor`.

| Режим | Блокировка BitTorrent Suricata | IP-баны guard |
|---|---|---|
| `enable` | Работает | Новые баны включены. |
| `monitor` | Работает | Новые баны не назначаются, прежние действуют до истечения срока. |
| `off` | Работает | Guard остановлен, его баны сняты. |
| [`disable` — трафик без анализа](#stop) | Остановлена, NFQUEUE снята | Guard остановлен, его баны сняты; маршруты TUN сохраняются. |
| [`uninstall` — удаление](#uninstall) | Службы и программа удалены | Баны, NFQUEUE и собственные маршруты удалены; сначала верни исходный профиль Xray. |

### Снять бан с одного IP

Укажи реальный забаненный IPv4 вместо `203.0.113.10`:

```bash
sudo nft delete element inet xray_client_ban clients_v4 '{ 203.0.113.10 }'
```

Остальные IP-баны сохраняются. Suricata продолжает проверять трафик. Для IPv6-адреса используется набор `clients_v6`.

<a id="allowlist"></a>
### Исключить IP из банов

В `/etc/xray-connection-guard/config.json` добавь нужный адрес или подсеть в существующий массив `firewall.allowlist_cidrs`, например `"203.0.113.10/32"`. Подставь свой адрес и сохрани остальные поля конфигурации.

Затем выполни `sudo bash manage.sh enable`. Исключение запрещает новые IP-баны этого адреса; если бан уже существует, сними его отдельно. Проверка BitTorrent Suricata остаётся включённой.

Адреса самой ноды определяются автоматически; частные и служебные IP guard не банит.

### Обновить установленный guard

В каталоге проекта на RU:

```bash
git pull --ff-only
sudo bash manage.sh install
sudo bash manage.sh enable
```

`git pull` обновляет исходники, `install` — установленные файлы в `/opt/xray-connection-guard/`, `enable` — конфиги инспекции и работающие службы. Сохранённый выбор TUN остаётся в силе.

После обновления начни новые клиентские подключения для проверки.

### Перезагрузка RU и перезапуск Xray

Guard и Suricata включены в автозапуск. Служба очереди запускается как зависимость Suricata; её отдельный `systemctl enable` не требуется.

Проверь также автозапуск самой ноды Xray. Для Docker это обычно обеспечивается существующей политикой `restart: always` или `restart: unless-stopped` в Compose.

При пересоздании TUN Xray назначает IPv4 через `gateway`, а помощник guard восстанавливает маршрут, правило и `rp_filter`. Проверка выполняется каждую секунду. После обычного перезапуска Xray ручные сетевые команды не нужны.

В TUN-режиме guard также подписывается на изменения интерфейсов и IP через Linux netlink. Поэтому появившийся заново адрес TUN учитывается при сопоставлении событий сразу, без ожидания очередной 10-минутной проверки адресов ноды.

При холодном запуске служба ждёт TUN до 60 секунд. Если Xray не успел запуститься и зависимые службы остались неактивны, дождись готовности ноды и повтори `sudo bash manage.sh enable`.

<a id="log-maintenance"></a>
### Как ведутся журналы

В Remnawave журнал Xray можно смотреть так:

```bash
sudo docker exec remnanode xlogs
```

Имя контейнера замени на своё. `Ctrl+C` завершает только просмотр журнала.

Guard читает файл контейнера через `/proc/<PID>/root`, сохраняя открытый файл и позицию чтения при рестарте Docker-контейнера. Записи за время переподключения не пропускаются; при смене файла дочитывается старый журнал и затем читается новый. Дополнительный bind mount журнала на хост не требуется.

Для журнала под Supervisor guard при старте и затем каждые 10 минут проверяет `stdout_logfile_maxbytes` в `/etc/supervisord.conf` контейнера. Лимит меньше 100 МБ, в том числе отсутствующий параметр со штатным лимитом 50 МБ, увеличивается до `100MB`, после чего контейнер перезапускается. При лимите 100 МБ или больше, а также `0` без ограничения размера, перезапуска по этой причине нет.

Проверка идёт в фоне. Ошибки и результат видны в журнале guard; при ошибке применения изменения попытка повторяется через 10 минут. Другие способы ведения журнала пропускаются.

<a id="stop"></a>
## Отключить анализ, сохранив трафик

На хосте RU из каталога проекта выполни:

```bash
sudo bash manage.sh disable
```

Команда останавливает guard и Suricata/nDPI, отключает их автозапуск, снимает IP-баны guard и удаляет только собственные NFQUEUE-правила. **Пакеты продолжают проходить через прежний TUN и выходную ноду, но без анализа и блокировки BitTorrent.** Профиль Xray, IPv4-маршрут, policy rule и `rp_filter` не удаляются и не откатываются. Повторный `disable` допустим.

Служба `xray-connection-guard-queue.service` остаётся включённой и работает **только как помощник маршрутизации**: восстанавливает маршруты при пересоздании TUN и после перезагрузки. Режим сохраняется в `/etc/xray-connection-guard/routing-only`; перезапуск/перезагрузка службы или повторный `install` не включают анализ обратно. Это намеренное отключение защиты, не режим мониторинга.

Для возврата анализа и банов выполни `sudo bash manage.sh enable`. Для анализа без новых IP-банов — `sudo bash manage.sh monitor`. Менять профиль Xray не требуется; эти команды снимают режим «только маршрутизация» и возвращают NFQUEUE.

<a id="uninstall"></a>
## Удалить guard

Для полного отката сначала в панели восстанови исходный профиль RU: публичный inbound снова отправляет трафик прямо в `TO_FREEDOM`. Убери `INSPECT_VIA_TUN`, `GUARD_TUN_IN` и связанные правила, примени профиль и проверь обычное подключение. Затем выполни:

```bash
sudo bash manage.sh uninstall
```

В отличие от `disable`, команда останавливает и отключает **все три службы**, удаляет их unit-файлы, `mode.conf`, установленные Python-скрипты, собственные NFQUEUE-правила и IP-баны. Удаляются собственные IPv4-маршрут и policy rule; прежний `rp_filter` восстанавливается, если тот же интерфейс существует и настройка не изменена вручную. Заимствованные и чужие маршруты сохраняются. Сам TUN-интерфейс принадлежит Xray и этой командой не удаляется.

**Сначала верни исходный профиль Xray:** `uninstall` не редактирует панель, профиль Xray или Docker. Если профиль всё ещё направляет пакеты в TUN-инспекцию, после удаления маршрутов такое подключение работать не будет.

Для повторной установки сохраняются `/etc/xray-connection-guard` с конфигурацией, журналы, резервные копии и движки Suricata/nDPI, включая собранные в `/opt/xray-connection-guard/engines`. Системные пакеты и каталог исходников проекта не удаляются. Повторный `uninstall` допустим; ошибка остановки службы или очистки сети завершает команду с ошибкой, без сообщения об успешном удалении. Для возврата выполни `install`, примени нужный профиль Xray и затем `enable`.

Не используй ручной `systemctl stop` очереди или `queue-off` для обычного отключения анализа: они очищают маршрутизацию. При аварии очереди в обычном режиме инспекции NFQUEUE остаётся fail-closed; `disable` явно переключает на пропуск трафика без проверки.

<a id="troubleshooting"></a>
## Если что-то не работает

Сначала собери состояние и последние ошибки на RU:

```bash
sudo systemctl status xray-connection-guard.service xray-ndpi.service xray-connection-guard-queue.service --no-pager -l
sudo journalctl -u xray-connection-guard.service -u xray-ndpi.service -u xray-connection-guard-queue.service -n 100 --no-pager
```

| Симптом | Что проверить |
|---|---|
| Нет `xray-guard` | Применён ли профиль к RU, есть ли TUN-inbound, поддерживает ли его ядро, доступны ли контейнеру TUN и `NET_ADMIN`. |
| Интерфейс есть, но нет IPv4 / `Set an IPv4 gateway` | Проверь ядро внутри контейнера RU: 26.3.27 игнорирует `gateway`, даже если он уже указан в JSON. Для проверенной схемы используй 26.11.9. Затем проверь `gateway`, свободную подсеть и применение профиля. |
| Ошибка про таблицу или приоритет `14817` | Посмотри `ip -4 rule show` и `ip -4 route show table 14817`. Чужие настройки нужно сначала разобрать; автонастройка их не перезаписывает. |
| `Xray access log not found` | Запущен ли Xray, включён ли access-журнал, используется ли host network. |
| Найдено несколько журналов Xray | Добавь к `enable` параметр `--container` с именем нужного контейнера. |
| `unknown protocol: tun` или ошибка TUN в Xray | Проверь версию ядра на RU и его журнал; используй проверенную версию для этой схемы. |
| Потоки блокируются, а IP-банов нет | Проверь порог 5 потоков / 5 IP, режим `enforce`, `email` и наличие access + INFO в одном источнике. |

### Если растёт access, но нет событий Suricata

Во время нового трафика через клиента:

```bash
sudo nft list table inet xray_guard_inspect
sudo cat /proc/net/netfilter/nfnetlink_queue
sudo tail -n 3 /var/log/xray-ndpi/eve.json
```

В TUN-режиме таблица должна содержать `oifname "xray-guard"` и `iifname "xray-guard"` с очередью `0`. Нулевые счётчики при клиентском трафике означают, что он не доходит до этой инспекции: проверь применённый профиль и порядок `routing.rules`.

Счётчики могут расти и на обычном трафике. Для BitTorrent-событий нужны распознанные потоки, не заблокированные раньше правилами самого Xray.

### Если события есть, но IP не сопоставлен

В журнале guard:

| Поле или сообщение | Значение |
|---|---|
| `alerts` | Подходящие события Suricata прочитаны. |
| `matched` | События сопоставлены с исходными клиентами. |
| `bans` | IP-баны успешно применены. |
| `no_access_for_peer` | Не найдена подходящая access-запись для пира. |
| `time_window` | Время найденной записи не подходит к началу потока. |
| `client_ip_missing` | В записи не удалось определить исходный IP клиента. |
| `multiple_client_ips` | Сопоставление неоднозначно: подходят разные IP клиентов. |
| `eve_ignored_server_ip` после рестарта Xray | Проверь, есть ли адрес TUN в `Node addresses detected/changed`. Обнови guard: старая версия могла не замечать пересозданный TUN до 10 минут. |
| `udp_socket_owner_missing` | Для UDP-сокета не найден первоначальный клиент; проверь общий access + INFO-журнал. |
| `udp_socket_unverified` | Сокет закрыт, переиспользован или его владелец больше не подтверждается. |

Guard использует `flow.start` Suricata, потому что распознавание может произойти позже начала соединения. Для UDP/XUDP дополнительно проверяются INFO-записи `proxy/freedom` и действующий сокет Linux. Неоднозначное сопоставление не приводит к IP-бану; Suricata при этом продолжает блокировать распознанный BitTorrent.

### Если установлена старая ручная версия с NFQUEUE 21

Отсутствие `/opt/xray-connection-guard/inspector.py` или службы `xray-connection-guard-queue.service` означает, что команды новой автонастройки к такой установке пока неприменимы. Выполни `install` из обновлённой копии проекта.

Старые сторонние правила NFQUEUE новая установка автоматически не удаляет. Посмотри их перед переходом:

```bash
sudo nft -a list ruleset
sudo iptables-save
sudo ip6tables-save
```

Удалять нужно конкретные правила старой инспекции. Не выполняй `nft flush ruleset` или `ip rule flush`: это затронет и остальную сеть сервера. Остановка Suricata при оставшейся NFQUEUE без `bypass` может остановить трафик через эту очередь.

Если нужно только отключить старую Suricata, сначала удали относящиеся к ней правила очереди `21`, затем выполни:

```bash
sudo systemctl disable --now xray-ndpi.service
```

Такой команде не нужны ни `inspector.py`, ни служба `xray-connection-guard-queue.service`. Если непонятно, какие правила принадлежат старой установке, сначала разбери вывод команд выше — удалять чужие правила нельзя.

<a id="direct"></a>
## Альтернатива: RU сама выходит через DIRECT

Этот раздел нужен, если пользователи выходят в интернет **на самой RU через outbound `freedom`**, а не через другой VLESS/XHTTP-outbound.

Для этого варианта выполни [установку guard](#install) командой `sudo bash manage.sh install --inspection-mark` и [настройку журналов](#logging). Xray также должен работать в сети хоста; для установки метки ему нужно право `CAP_NET_ADMIN`. TUN-блоки основной инструкции здесь не добавляются; ограничение версии для TUN в этом режиме не применяется.

В каждый используемый `freedom`-outbound добавь поле `streamSettings.sockopt.mark`. Пример одного outbound:

```json
{
  "tag": "DIRECT",
  "protocol": "freedom",
  "settings": {},
  "streamSettings": {
    "sockopt": {
      "mark": 1481785689
    }
  }
}
```

Оставь свой `tag`, существующие `settings` и остальные параметры; добавляется именно поле `mark` со значением `1481785689`.

Примени профиль и запусти на хосте RU:

```bash
sudo bash manage.sh enable --inspection-mark
```

Если переходишь с TUN, перед этим восстанови рабочий профиль с прямым выходом. Проверка служб, журналов и IP-банов остаётся такой же.

Метка на зашифрованном `TO_FREEDOM` не показывает внутренний BitTorrent-трафик. Для схемы с выходной нодой используй основную TUN-инструкцию.

## Где находятся файлы

| Путь | Содержимое |
|---|---|
| `/opt/xray-connection-guard/` | Установленные исполняемые файлы; обновляются через `manage.sh install`. |
| `/etc/xray-connection-guard/config.json` | Настройки guard и сохранённый выбор интерфейса. |
| `/etc/xray-connection-guard/suricata.yaml` | Сгенерированная конфигурация инспекции Suricata. |
| `/var/log/xray-connection-guard/audit.jsonl` | Аудит инцидентов и IP-банов. |
| `/var/log/xray-ndpi/eve.json` | События Suricata для guard. |
| `config/xray-tun.fragment.json` в репозитории | Пример объектов для ручного добавления в профиль Xray. |

Изолированные проверки и команды для разработчиков описаны в [tests/README.md](tests/README.md). Стенд проверяет IPv4 TCP/UDP, реальные Suricata/nDPI и Xray TUN, IP-баны на 600 секунд, пересоздание TUN и отсутствие обхода при недоступности Suricata, TUN или выходной ноды.

Отдельный [прогон VLESS/RAW/REALITY с Vision](tests/results/vless-raw-vision.json) между двумя изолированными Xray подтвердил блокировку TCP BitTorrent и DHT, а также IP-баны на 600 секунд.

[Проверка настоящего внешнего VLESS-выхода](tests/results/external-vless.json) от 27.11.2026 с исправленной ссылкой **без `flow`** также прошла: HTTPS/DNS через внешний адрес, реальные блокировки TCP BitTorrent/DHT, два IP-бана на 600 секунд и сохранение трафика контрольного клиента. При остановке Suricata или запрете подключения к внешней ноде обхода через DIRECT нет. Первая ссылка с `xtls-rprx-vision` не передавала HTTP/HTTPS даже без инспекции; этот неудачный прогон не относится к исправленной ссылке. Ограничения и точная схема внешнего теста указаны в отчёте.

Для Marzban 0.8.4 отдельно выполнена [проверка в Docker с настоящим systemd](tests/results/marzban-docker.json), включая холодный старт и потерю SSH при ошибочном глобальном default route. Это проверка изолированного стенда с тестовым трафиком, не гарантия для произвольного рабочего профиля или другой версии панели.
